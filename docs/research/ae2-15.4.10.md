# AE2 15.4.10 (Forge / MC 1.20.1) 自动合成内部机制研究报告

> 面向目标：编写一个 Forge 附属模组，通过 Mixin 介入 AE2 的自动合成，以支持**概率副产物（chance byproduct）**处理模式。
>
> 目标功能：
> 1. 当合成任务的**处理样板**输出包含概率副产物（例如 100% 产物 A + 50% 产物 B，样板把 A、B 都登记为输出）时，若当前任务**并不需要 B**，CPU 不应无限等待 B；
> 2. 若任务**确实需要 B**，应能把样板**反复下推**到机器，直到 B 真正产出；
> 3. 网络应能读取并使用这类副产物输出——玩家请求 B 时能通过该样板自动合成；
> 4. 样板供应器（或对其的 Mixin）应能知道"当前是哪个合成任务/CPU 正在下推样板"，从而查询该任务对某个 key 的剩余需求。

### 1.3 谁来消费 `waitingFor`（哪些产出才算"到达"）

`CraftingCpuLogic.insert(AEKey what, long amount, Actionable type)`（:261-322）：

### 1.4 任务完成 vs 作业完成的判定

* **单个任务（pattern task）完成**：`CraftingCpuLogic.executeCrafting` 中 `task.getValue().value--` 后 `if (value <= 0) it.remove();`（:229-233）。`TaskProgress` 只保存 `long value`（剩余下推次数），任务表 `Map<IPatternDetails, TaskProgress>`（`ExecutingCraftingJob.java:43`）。
* **整个作业完成**：**唯一**入口是 `insert()` 中 `job.remainingAmount <= 0 → finishJob(true)`（:304-305）。
  * `finishJob(boolean success)`（:325-363）：`job.link.markDone()/cancel()` → `job.waitingFor.clear()`（:335）→ 对所有任务的输出 `postChange(...)` → `notifyJobOwner(...)` → `this.job = null` → `storeItems()`。
  * **没有任何轮询式 `isJobDone()`**：作业完成完全由"最终产物到货"驱动。
  * `finishJob(false)` 只由 `cancel()`（:356-365）调用。

> **重要推论**：`waitingFor` 里滞留的 B **本身不会阻止作业结束**（作业结束只看 `finalOutput` 的 `remainingAmount`）。它造成的问题有三类：
> (i) `ElapsedTimeTracker` 的进度/预计时间永远不满（`startedWorkByType` 计入了 B，`completedWorkByType` 永远不增；`ElapsedTimeTracker.getProgress()` 见 `ElapsedTimeTracker.java:114-126`，`decrementItems`/`addMaxItems` 在 :82 / :92）；
> (ii) `ICraftingService.isRequesting(B)` / `getRequestedAmount(B)` 长期为真（`CraftingService.java:442-455`、`currentlyCrafting` 由 `getAllWaitingFor` 填充 :165-168）；
> (iii) **真正的死锁**：若 B 在计划中确实是下游某个任务的输入（`CraftingTreeNode` 对 B 会走 `extract` 路径），而 B 因概率没产出，则该下游任务永远凑不齐输入而无法下推；若 B 就是最终产物，则 `remainingAmount` 永不减少，作业永不结束。

## 2. Mixin 方案（Task 2）

### 2.1 是否可获得"逐 key 剩余需求"？

**AE2 没有现成的 per-key demand**。`waitingFor` 只是"期望到货量"，不含"是否真的需要"。但在 `executeCrafting` 的注入点，**可获得的信息**足以自行推算，且相当准确：

在 `CraftingCpuLogic.executeCrafting` 内可访问：

1. `this.job`（`@Shadow private ExecutingCraftingJob job;`）；
2. `job.finalOutput`（`GenericStack`）与 `job.remainingAmount`（`long`）→ **最终产物剩余需求**；
3. `job.tasks`（`Map<IPatternDetails, TaskProgress>`）→ 每个样板还有多少次没下推；
4. 每个 `IPatternDetails.getInputs()` → `IInput.getPossibleInputs()` / `getMultiplier()` → **未来还要消耗什么、消耗多少**；
5. `job.waitingFor`（已期望到货量）、`inventory`（`ListCraftingInventory`，CPU 本地库存）。

推荐的"剩余需求"近似函数（保守、单调、不会误删）：

```java
// 伪代码：key 是否仍被"当前作业"需要
static boolean isStillDemanded(AEKey key, ExecutingCraftingJob job) {
    // 1) 最终产物仍有剩余量
    if (job.finalOutput != null && job.remainingAmount > 0 && key.matches(job.finalOutput))
        return true;
    // 2) 任一"尚未推完"的任务，其任一可能输入匹配 key（保守：忽略倍率，只看是否可能出现）
    for (var e : job.tasks.entrySet()) {
        if (e.getValue().value <= 0) continue;                 // 该任务已推完
        for (var in : e.getKey().getInputs())
            for (var possible : in.getPossibleInputs())
                if (key.matches(possible)) return true;
    }
    return false;
}
```

更精细的版本用需求量而不是布尔值：

```java
long demand = 0;
if (job.finalOutput != null && key.matches(job.finalOutput)) demand += job.remainingAmount;
for (var e : job.tasks.entrySet()) {
    long remaining = e.getValue().value;                 // 剩余下推次数
    if (remaining <= 0) continue;
    for (var in : e.getKey().getInputs()) {
        for (var possible : in.getPossibleInputs()) {
            if (key.matches(possible)) { demand += in.getMultiplier() * possible.amount() * remaining; }
        }
    }
}
// 再减去 CPU 本地库存与已在途量，得到"净缺口"
long net = demand - cpu.getStored(key) - cpu.getWaitingFor(key);
```

要点：

* **必须**把 `finalOutput`/`remainingAmount` 计入（最终产物的 `waitingFor` 正是通过样板输出累加进来的，删掉它会让作业永不结束）；
* 保守判定（"是任一存活任务的可能输入"）已足够解决需求 1，且不会破坏正常流程；
* `job.tasks` 的 key 是 `IPatternDetails`（`equals/hashCode` 由 `definition` 决定，`AEProcessingPattern.java:47-54`），因此与 `executeCrafting` 里的 `details` 可直接比较。

**不确定性说明**：`demand` 是"计划层面"的剩余需求，未考虑"CPU 本地库存已能满足该需求"的情况（`getStored` 可补正）。另外 `tasks` 中可能存在已无剩余价值但 `value > 0` 的任务（例如其输入永远凑不齐），此时会保守地要求等待——属于**安全方向**的偏差（宁可等，不可错删）。

### 2.2 推荐的最小 Mixin 集合

**目标 A：把"当前作业不需要的 key"从 `waitingFor` 中排除**

不要 `@Redirect` `job.waitingFor.insert`（`executeCrafting` 内有 **2 处**同签名调用 :217/:221，且 `@Redirect` 会与其他模组冲突）。推荐注入**唯一**产生 `expectedOutputs` 的地方：

```java
@Mixin(value = CraftingCpuHelper.class, remap = false)
public class CraftingCpuHelperMixin {
    // 目标: public static KeyCounter[] extractPatternInputs(IPatternDetails, ICraftingInventory, Level, KeyCounter, KeyCounter)
    // 描述符: (Lappeng/api/crafting/IPatternDetails;Lappeng/crafting/inv/ICraftingInventory;Lnet/minecraft/world/level/Level;Lappeng/api/stacks/KeyCounter;Lappeng/api/stacks/KeyCounter;)[Lappeng/api/stacks/KeyCounter;
    @Inject(method = "extractPatternInputs", at = @At("RETURN"), remap = false)
    private static void ae2byp$filterExpectedOutputs(IPatternDetails details, ICraftingInventory inv, Level level,
            KeyCounter expectedOutputs, KeyCounter expectedContainerItems,
            CallbackInfoReturnable<KeyCounter[]> cir) {
        if (cir.getReturnValue() == null) return;               // 输入没凑齐，本就不会用到 expectedOutputs
        var job = CraftingJobContext.current();                 // 由下面的 hook 设置；可能为 null（外部调用）
        if (job == null) return;
        for (var key : new ArrayList<>(expectedOutputs.keySet())) {
            if (!isStillDemanded(key, job)) {
                expectedOutputs.remove(key);                    // KeyCounter.remove(AEKey): long
            }
        }
    }
}
```

配套：把当前 `ExecutingCraftingJob` 暴露为上下文（`CraftingCpuLogic.executeCrafting` 的 HEAD/RETURN）：


`CraftingJobContext` 建议用 `ThreadLocal<Deque<ExecutingCraftingJob>>`（或 `ThreadLocal<ExecutingCraftingJob>` + 深度计数）。

**目标 B：让"只有被需要的产出到货"即可算完成**

* **无需再改完成判定**：完成只看 `finalOutput.remainingAmount`（§1.4）。只要保证(1) 最终产物 key 永远不被过滤掉（`isStillDemanded` 已包含该条），(2) 未被需要的副产物不再进入 `waitingFor`，那么"B 没到货"就不再污染进度、不再置 `isRequesting(B)`、也不会卡住下游任务。
* 若还希望"作业在只剩未被需要的期望产出时立即结束"，可再加一个**兜底**注入（可选）：

```java
// 目标: public long insert(AEKey, long, Actionable) —— 在最终产物到货后，允许清掉"已无需求"的 waitingFor 条目
@Inject(method = "insert", at = @At("TAIL"), remap = false)
private void ae2byp$pruneWaitingFor(AEKey what, long amount, Actionable type, CallbackInfoReturnable<Long> cir) {
    if (this.job == null) return;
    for (var key : new ArrayList<>(this.job.waitingFor.list.keySet()))
        if (!isStillDemanded(key, this.job)) this.job.waitingFor.list.remove(key);
}
```
（`waitingFor.list` 是 `public final KeyCounter`，可直接操作。）

**目标 C（需求 2）：任务确实需要 B 时，反复下推样板**

这**不是** CPU 侧能靠"过滤"解决的，属于**供应器侧策略**，需要：

1. 在 `pushPattern` 成功时记录 `(provider, patternDetails, job/CPU, 期望的副产物 key, 剩余需求)`；
2. 在后续 tick 检查机器/返回库存是否产出了 B；
3. 若未产出且需求仍在，则**再次下推**同一 `patternDetails`（可复用 `PatternProviderLogic` 的 `getPatternInv()` / 目标 `PatternProviderTarget.insert` 直接推送，或通过 `ICraftingProvider` 提供"合成外"的额外推送通道）。

CPU 侧只需保证：**B 仍在 `waitingFor`**（因为此时 `isStillDemanded(B) == true`，过滤不会删它），以及不要因"任务已推完"而放弃——注意 `task.value` 递减到 0 后任务即被 `it.remove()`（:229-233），**AE2 不会主动重推**。所以重推逻辑必须完全由附属模组持有（见 §5、§8）。

> **替代（更简）方案**：不改 `waitingFor`，而是把"概率副产物"这一类输出**从样板输出中彻底剔除**（在 `PatternProviderLogic.updatePatterns()` / `decodePattern` 之后不改变样板本体，而是在附属模组的 `IPatternDetails` 包装层里只报 100% 输出），B 则通过**另一个独立样板**（把 B 放第一位作为 primary output）来提供自动合成能力。这样：
> * `waitingFor` 天然只含必然产物 → 需求 1 自动满足；
> * 需求 3 由"B 为主输出的样板"满足（见 §7 的结论，这**必须**有代码支持）；
> * 需求 2 的重推仍需供应器侧策略。
> 该方案不触碰 AE2 的 `waitingFor` 语义，风险最低；缺点是同一台机器同一个样板会同时存在两条样板定义。

### 3.2 是否在 tick 内？可否重入/交错？

* **是**：整条链在**服务器主线程**的网格 tick 中同步执行（`onServerEndTick`，由 `IGridServiceProvider` 机制调用）。同一 tick 内先 `updateCPUClusters()`（如需），再**顺序** `for each cpu` 调 `tickCraftingLogic`。因此**多个 CPU 不会交错**，`usedOps` 也是每 CPU 私有数组。
* **存在嵌套调用（同线程、非重入 `executeCrafting`）**：
  * `provider.pushPattern` 内部会调用 `sendStacksOut()`（`PatternProviderLogic.java:496-530`）→ `PatternProviderTarget.insert` → 相邻方块的 `MEStorage.insert`。若相邻是**另一个 ME 网络**的存储，则会走到那个网络的 `StorageService` → `CraftingServiceStorage` → `insertIntoCpus` → 那个网络 CPU 的 `CraftingCpuLogic.insert`（`insert` **不会**回调 `executeCrafting`）。
  * `ICraftingMachine.pushPattern(...)`（`PatternProviderLogic.java:320-326`，如分子装配室或 GTCEu 机器）可能同步产出并把物品塞进供应器的返回库存；返回库存的网络注入发生在供应器**自己的 grid ticker**（`PatternProviderLogic$Ticker` → `doWork()`，:542-546），**不是**在下推内联发生的。
* **结论**：用 `ThreadLocal` 记录"当前正在下推的 job"是安全且正确的；用单一 `static` 字段在**同一线程**内也基本安全，但 `CraftingCalculation` 在独立线程池（"AE Crafting Calculator"，`CraftingService.java:53-66`）执行，且**不会**调用 `pushPattern`，因此 `static` 字段的主要风险只是"嵌套/异常未清理"，`ThreadLocal` + `try/finally`（用 HEAD/RETURN 注入即可）更稳。

### 3.3 给供应器注入上下文的三种做法（推荐度从高到低）

1. **ThreadLocal 上下文（推荐）**：`executeCrafting` HEAD/RETURN 设置/清理 `ExecutingCraftingJob`（§2.2 的 `CraftingJobContext`）。供应器在 `pushPattern` 内通过 `CraftingJobContext.current()` 读取。**无需改动任何 AE2 签名**，零冲突。
2. **捕获 CPU 引用后异步查询**：在 `pushPattern` 中记下 `CraftingCPUCluster`（可从 `CraftingJobContext` 的 job → 但 job 不含 cluster 反向引用；实际应从上下文直接存 `CraftingCpuLogic`，其 `cluster` 字段为包私有，需 `@Accessor`）。之后在 ticker 里用 `cluster.craftingLogic.getPendingOutputs(key)` / `getWaitingFor(key)` / `hasJob()` 查询。`CraftingCPUCluster.craftingLogic` 是 **`public final`**（`CraftingCPUCluster.java:74`），`getCpus()` 返回 `ICraftingCPU`，可直接强转。
3. **接口注入**：自定义 `interface CraftingContextHolder { void ae2byp$setJob(ExecutingCraftingJob job); }`，用 Mixin `implements` 加到 `PatternProviderLogic`，在 `pushPattern` 前由上下文写入。适合需要在供应器上长期保存"最近一次下推属于哪个作业"的场景。

## 4. 多余/计划外物品的处理（Task 4）

### 4.1 `CraftingCpuLogic.insert` 的行为（唯一入口）

（代码见 §1.3，`CraftingCpuLogic.java:261-322`）

| 情形 | 行为 |
| --- | --- |
| key **不在** `waitingFor`（完全没预期的物品） | `waitingFor <= 0` → **立即 `return 0`**，不消耗、不入 CPU 库存。返回值 0 表示"没接收"，**调用链上层的存储服务会继续尝试下一个存储提供者 → 物品进入普通 ME 存储**（不会被销毁） |
| key 在 `waitingFor`，但到货量 **> 期望量** | 先把 `amount` **裁剪**为 `waitingFor`，只按裁剪后的量记入 CPU，`return inserted`（= 裁剪后量）。超出部分由上层存储服务**继续投递到普通 ME 存储**。同样**不会销毁** |
| key 在 `waitingFor` 且在量内，且 `key.matches(job.finalOutput)` | 走 `job.link.insert(...)`（投递给 requester），并 `job.remainingAmount -= amount`，可能触发 `finishJob(true)`。注意代码注释明确说明：**忽略任何余量**（没有 requester 时余量可能"被丢弃"于 CPU 记账，但物品是交给 link/网络的） |
| 其他 | `inventory.insert(what, amount, MODULATE)` → 进 CPU 本地库存，之后再存回网络 |

### 4.2 `postChange` 是什么（任务描述中的误解）

`CraftingCpuLogic.postChange` 是**私有**方法（`:395-400`），**只用于通知菜单监听器**，与"插入物品"无关：

```java

}
```
`listeners` 是 `Set<Consumer<AEKey>>`（:75），注释说明"**仅供菜单使用**"（`addListener` :435-441）。

### 4.3 物品如何真的回到网络：`storeItems()`

`storeItems()`（`:370-393`）在 `job == null` 时被 `tickCraftingLogic` 调用，也由 `finishJob` 调用：


**结论（Task 4）**：多余或计划外物品**不会被 void**，会（1）先被喂给 CPU 的 `waitingFor`，未被接纳的部分（2）进入普通 ME 存储；网络满则暂留在 CPU 本地库存或供应器返回库存。

### 6.3 概率/百分比：**AE2 15.x 的处理样板完全不支持概率**

* `ProcessingPatternEncoding`（**包私有 `class`**，`crafting\pattern\ProcessingPatternEncoding.java`）只有两个 NBT 键：
  ```java
  private static final String NBT_INPUTS  = "in";    // :35
  private static final String NBT_OUTPUTS = "out";   // :36
  ```
  `encodeProcessingPattern(CompoundTag tag, GenericStack[] sparseInputs, GenericStack[] sparseOutputs)` 写入 `tag.put("in", ListTag)` / `tag.put("out", ListTag)`（:67-70）；每个元素是 `GenericStack.writeTag(stack)`。
* `GenericStack.writeTag`（`api\stacks\GenericStack.java:59-66`）：
  ```java
  var tag = stack.what.toTagGeneric();   // = toTag() + tag.putString("#c", keyTypeId)
  tag.putLong("#", stack.amount);
  ```
  即每个元素形如 `{ <key 的 tag…>, "#c": "ae2:i" 或 "ae2:f" … , "#": <amount> }`；`"#"` 是**数量**，`"#c"` 是 **AEKeyType id**（`AEKey.java:43-61, 105-109`）。

* 所以**没有任何 chance / probability / weight 字段**。要在样板里携带"50%"，只能：(i) 把概率写在**样板物品自身的自定义 NBT**里（`ProcessingPatternItem` 的 tag 与 `in`/`out` 平级，可加自定义键，AE2 解码时会忽略未知键——但 `AEProcessingPattern` 构造器只读 `in`/`out`，所以附加键**不会**被 AE2 使用，只会被你的附属模组读取）；(ii) 维护外部映射（样板物品 NBT / 物品 ID + 数据 → 概率表）；(iii) 通过"多条样板/多档输出"表达。 **结论：AE2 本身没有 chance 概念，附属模组必须自建存放位置。**
* 相关常量（`CraftingPatternEncoding` 才有）：`"crafting"`（boolean）与 `"substitute"`（boolean）——见 `InvalidPatternHelper` 构造器读取 `in`/`out`/`crafting`/`substitute`（`crafting\pattern\InvalidPatternHelper.java:47-56`）。

### 6.4 引用了"游戏注册表中不存在的物品"时如何处理

链路（**已核实，结论明确**）：

1. `ProcessingPatternEncoding.getMixedList(nbt, key, maxSize)`（:48-65）对每个元素调用 `GenericStack.readTag(entry)`； `GenericStack.readTag`（`GenericStack.java:47-57`）：`AEKey.fromTagGeneric(tag)` 返回 null（例如 `"#c"` 缺失，或该 key type / 物品已不存在，见 `AEKey.java:43-61`）→ **返回 null**；
2. 于是 `getMixedList` **抛异常**：`throw new IllegalArgumentException("Pattern references missing stack: " + entry);`（:61）；
3. `AEProcessingPattern` 构造器因此抛出；
4. `ProcessingPatternItem.decode(AEItemKey what, Level level)` 用 **`try { return new AEProcessingPattern(what); } catch (Exception e) { return null; }`** 兜住（`crafting\pattern\ProcessingPatternItem.java:31-38`）→ 返回 **null**；
5. `PatternDetailsHelper.decodePattern(...)` 返回 null → 下游：
   * `PatternProviderLogic.updatePatterns()`（:250-268）**跳过**该样板（不加入 `patterns`），因此它既不可合成也不会被下推；
   * `EncodedPatternItem.appendHoverText`（客户端）检测到 `details == null`，把物品名染红为 `GuiText.InvalidPattern` 并用 **`InvalidPatternHelper`** 渲染"产物/原料"提示（`EncodedPatternItem.java:113-146`）。`InvalidPatternHelper` 是**包私有**类，且**只用于 tooltip**：它读 `in`/`out`/`crafting`/`substitute`，对无法解析的条目退化为读 `id` / `Count` / `Damage` 显示红色（`InvalidPatternHelper.java:88-105`）。

**含义**：如果副产物 B 的物品在整合包里根本不存在，样板会**整体失效**（连 A 也不能自动合成）。因此副产物必须是**真实注册的物品**。

### 7.2 判定（明确结论）

**(1) "计划内部把副产物 B 当作可用产出" —— 是，AE2 已经做到了。** `CraftingTreeProcess.request` 把所有 `getOutputs()` 元素插入模拟库存，因此：

* 若同一棵合成树中有任务需要 B 作为输入，B 可以被副产物满足（**注意顺序**：`request` 先请求输入再把输出插入模拟库存，所以只有**在时间上更晚**被处理的任务才能用上这批 B；兄弟分支/更早的分支拿不到）；
* 因此"同一棵树内复用副产物"不需要额外代码。

**(2) "把 B 单独作为一个可自动合成的目标（玩家请求 B）" —— 不，AE2 做不到，必须写代码。** 决定性证据在 `NetworkCraftingProviders.ProviderState.mount`（`me\service\helpers\NetworkCraftingProviders.java:161-180`）：


* `craftableItems`（以及模糊查找用 `craftableItemsList`）**只以 `getPrimaryOutput()`（= `getOutputs()[0]`）为键**注册；`getCraftingFor(key)` / `isCraftable(key)` / `getCraftables(filter)` 全部查这个表。
* 于是"样板里第 2 个及之后的输出（副产物）"在合成服务里**完全不可见**：
  * 合成终端不会把 B 标为可合成；
  * `ICraftingService.isCraftable(B)` 为 false；
  * 玩家请求 B → `CraftingTreeNode` 对 B 调 `getCraftingFor(B)` 得到空集合 → 无子样板 → `CraftBranchFailure` / 模拟时记入 `missing`。

**最终判定（Task 7）**：
> **"网络能读取样板里写的副产物 B" 这件事，AE2 只在"同一合成计划内部当作可用产出"这一层面已经处理；但"玩家请求 B 时用该样板自动合成 B"是 AE2 不支持的，需求 3 必须有代码。**

### 9.2 Mixin 配置命名

* AE2 自身的 mixin 配置：**`ae2.mixins.json`** + `ae2.mixins.refmap.json`（jar 根目录），mixin 类放在包 `appeng.mixins.*`（如 `appeng.mixins.ItemEntityMixin`、`appeng.mixins.chunkloading.*`）。**附属模组没有必须遵循的约定**，取自己的 `mixins.<yourmodid>.json` 即可；若需在 AE2 类上注入，**不必**声明 AE2 的 mixin config，只要在 `MixinConfigs` 里声明你自己的配置，并把 `package` 指向自己的 mixin 包。
* 建议在 `@Mixin(...)` 上加 `remap = false`（AE2 类名/方法名都是被 SRG 重映射过的模组代码，`remap = false` 对模组目标是标准做法；方法名在运行时是 `m_xxx_` 还是原名取决于 Forge 官方映射，实测时优先 `remap = false` 并核对 `javap` 输出——本报告中 `javap -p` 显示的是**源码名**，说明该 jar 使用官方（Mojang）映射）。
* mod id：**`ae2`**。可通过 `ModList.get().getModContainerById("ae2")` 或依赖 `mods.toml` 的 `[[dependencies.<yourmod>]] modId="ae2" versionRange="[15.4.10,)"` 约束。

## 12. 面向实现的最小结论清单

| 需求 | 是否必须写代码 | 推荐做法 |
| --- | --- | --- |
| (1) 不需要 B 时 CPU 不等待 B | **是** | ① `CraftingCpuLogic.executeCrafting` HEAD/RETURN 建 `ThreadLocal` 上下文；② `CraftingCpuHelper.extractPatternInputs` `@At("RETURN")` 过滤 `expectedOutputs`（用 `finalOutput/remainingAmount + job.tasks` 的保守需求判定） |
| (2) 需要 B 时不断重推 | **是** | 供应器侧策略：`pushPattern` 成功时记录 `(cpu/job, pattern, B, 需求)`；ticker 里用 `cpu.getPendingOutputs(B)`/`getWaitingFor(B)`/`hasJob()` 判定后重推（AE2 自己不会重推：`task.value` 归零即 `it.remove()`） |
| (3) 玩家可请求 B 并自动合成 | **是** | 必须让 B 成为某个样板的 `getPrimaryOutput()`（= `getOutputs()[0]`）：要么注册以 B 为主输出的等价样板，要么 Mixin `NetworkCraftingProviders.ProviderState.mount/unmount`（或兜底 `getCraftingFor`）把非主输出也注册为 craftable |
| (4) 供应器知道"当前作业/需求" | **是** | §8.2 的 `ThreadLocal<CraftingCpuLogic>` + `@Accessor("job")`；跨 tick 时持有 `CraftingCpuCluster`/`CraftingCpuLogic` 并每次校验 `hasJob()` 与 link id |
| 概率数值的存放 | **是** | AE2 处理样板 NBT 只有 `"in"` / `"out"`（元素为 `{#c: keyType, #: amount, …}`），**无 chance 字段**；需自建（样板自定义 NBT 或外部映射） |
| 副产物在同一计划内被复用 | 不需要 | `CraftingTreeProcess.request` 已把所有输出计入模拟库存（注意处理顺序） |
