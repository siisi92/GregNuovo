## 1. 起点：需求与澄清

### 1.1 原始需求（`需求.txt`，747 字节）

* 版本：1.20.1 / Forge 47.4.10 / GTM 7.3.0；名称：GregTech:AE
* ① 配方涉及不消耗物品时，配方结束后 AE 会把它们收回
* ② 配方涉及编程电路时，AE 自动把机器变成对应电路后再输入物品
* ③ 概率产物一次没出就继续投料，直到产出
* ④ 样板里编了概率产物但合成不需要时，直接停止投料，不必等待
* ⑤ AE 网络能读到样板内写出的副产物
* 「如果有疑问先不要写，先问我，没有疑问了再写」

### 1.2 第一轮澄清（架构层面，8 个问题）

| 问题 | 你的选择 |
| --- | --- |
| 逻辑挂在哪 | **单体走 AE2 样板供应器 + 多方块走样板总成**（两者都要） |
| 是否允许 Mixin 上游内部类 | **允许**（否则需求③④做不到） |
| 编程电路怎么编码/处理 | 样板输入里放编程电路，**不作为物品推送**、写进电路槽、不消耗网络库存 |
| 样板没有电路时 | **清零**机器电路 |
| "不消耗物品"如何判定 | 一次合成结束后，把**本次推送但未被消耗**的余料退回 |
| 概率产物重试规则 | **只对概率产物重试**（非概率产物缺失视为配方不匹配，不重试） |
| "合成不需要"如何判定 | **看当前合成任务的需求**：不在需求里 → 主产物到手即完成 |
| 交付形式 | 离线编译出 jar + 完整源码，AE2 按 15.4.10 编译 |

### 1.3 第二轮澄清（载体与粒度，4 个问题）

| 问题 | 你的选择 |
| --- | --- |
| 单体侧载体 | **Mixin 原版 AE2 样板供应器**（不新增方块） |
| 多方块侧载体 | **改造 GTM 原生 ME样板总成** |
| 电路粒度 | **每个样板槽独立电路**（推料前写入，完成后清除） |
| 概率信息来源 | **由 mod 从 GT 配方自动推断** |

### 1.4 由此确定的硬约束

1. 不新增任何方块/物品 → 只能注入，不能靠"新机器"绕开问题；
2. 必须兼容**两种完全不同的推料路径**（AE2 供应器 / GTM 样板总成）；
3. 概率信息在 AE2 样板里**不存在**（样板 NBT 只有 `in`/`out`），必须回到 GT 配方里找；
4. 需在 1.20.1 + GTM 7.3.0 + AE2 15.4.x 的**真实 API** 上落地（不能靠文档臆测）。

## 3. 上游调研：先读懂，再动手

### 3.1 关键教训：GitHub HEAD ≠ 你手上的版本

第一版设计曾参考 GitHub `1.20.1` 分支的 `MEPatternBufferPartMachine`，结果发现它用的 `brachy.modularui`、`sync_system`、`BlockEntityCreationInfo` 在 **7.3.0 的 jar 里根本不存在**。从此确立规则：**一切以上游 tag `v7.3.0-1.20.1` 的源码 + 本地同版本 jar 为准，双核对。**

### 3.2 调研方式

* 用两个子代理分别精读 GTM 7.3.0（tag `v7.3.0-1.20.1`）与 AE2 15.4.10（tag `forge/v15.4.10`）；
* 逐字保存上游源码到 `refsrc/`（GTM 106 个文件、AE2 40 个文件），保证后续有据可查；
* 产出两份中文调研报告：`docs/research/gtceu-7.3.0.md`、`docs/research/ae2-15.4.10.md`
  （含精确类名、方法描述符、字段、行号与负向结论"什么不存在"）。

### 3.3 决定实现方式的 10 条结论

| # | 结论 | 影响 |
| --- | --- | --- |
| 1 | GT 的 `notConsumable` 用 **`Content.chance == 0`** 表示（不是"0% 概率"） | 需求①的判定依据 |
| 2 | 概率 100% = `ChanceLogic.getMaxChancedValue()`（10000），判真概率用 `Content#isChanced()` | 需求③④的判定依据 |
| 3 | 电路槽**不能**用 Forge `ITEM_HANDLER` 写（`capabilityIO=NONE`），必须 `setStackInSlot` | 需求②的写法 |
| 4 | 电路在 GT 里**从不被消耗**（`RecipeRunner` 把它排除在待消耗列表外） | 需求②"不需要库存"成立 |
| 5 | 精确的"配方完成"边沿是 `RecipeLogic#onRecipeFinish()` | 需求①③的触发时机 |
| 6 | GTM 样板总成把**同一个共享电路槽**加进全部 27 个样板槽 | 需求②"每槽独立电路"必须替换它 |
| 7 | `InternalSlot#refund()` 只被两个 private 方法调用（GUI 按钮、换样板） | 需求①多方块侧可直接调用它 |
| 8 | AE2 **只按主产物**（`getOutputs()[0]`）登记可合成项 | 需求⑤必须有 mixin（否则请求副产物找不到样板） |
| 9 | AE2 的 `waitingFor` **无条件**把所有输出计入，且**不参考任务是否需要** | 需求④的实现点 |
| 10 | AE2 里"多余/计划外物品"不会被 void，会落回普通 ME 存储 | 需求③重试产生的多余主产物是安全的 |

## 4. 架构设计

### 4.1 三种推料拓扑（后来成为 1.0.1 修复的关键）

| 供应器紧挨的方块 | itemHost（收料/退料） | workMachine（跑配方） | 电路写到 |
| --- | --- | --- | --- |
| GT 单方块机器 | 机器本体 | 机器本体 | 机器电路槽 |
| 输入总线 / ME输入总线 | 该总线 | 所属多方块控制器 | 总线的电路槽 |
| GTM ME样板总成 | 样板总成缓冲 | 所属控制器 | 各样板槽的虚拟电路槽 |

### 4.2 分层

```
core/   纯逻辑层（无 Mixin）：目标识别、退料、重试、需求判定、诊断
hook/   所有 Mixin 的统一入口 GNHooks
mixin/  AE2 / GTM 注入点，只做"转发 + 状态读写"
```

### 4.3 11 个注入点

| Mixin | 目标 | 注入 | 用途 |
| --- | --- | --- | --- |
| `PatternProviderLogicMixin` | AE2 `PatternProviderLogic` | `pushPattern` HEAD/RETURN | 写电路、剥电路、登记跟踪 |
| `CraftingCpuLogicMixin` | AE2 `CraftingCpuLogic` | `executeCrafting` HEAD/RETURN | 建立"这次推送属于哪个合成任务"的上下文 |
| `CraftingCpuHelperMixin` | AE2 `CraftingCpuHelper` | `extractPatternInputs` RETURN；`tryExtractInitialItems` 内 `MEStorage.extract` Redirect | 需求④过滤；需求②电路免库存 |
| `NetworkCraftingProvidersMixin` | AE2 `NetworkCraftingProviders` | `addProvider`/`removeProvider` TAIL；`getCraftingFor`/`getCraftableKeys`/`getCraftables` RETURN | 需求⑤副产物可合成 |
| `CraftingCpuLogicAccessor` / `ExecutingCraftingJobAccessor` / `TaskProgressAccessor` | AE2 内部类 | `@Accessor` | 读取需求判定所需状态 |
| `MEPatternBufferMixin` | GTM `MEPatternBufferPartMachine` | `pushPattern` HEAD/RETURN；`onPatternChange` HEAD | 多方块侧需求①②③④ |
| `MEPatternBufferAccessor` | 同上 | `@Accessor("detailsSlotMap")` | 样板 → 样板槽下标 |
| `SlotRHLMixin` | `InternalSlotRecipeHandler$SlotRHL` | `<init>` TAIL | 需求②每槽独立电路 |
| `RecipeLogicMixin` | GTM `RecipeLogic` | `onRecipeFinish` TAIL | 精确捕捉配方完成 |

### 4.4 几个关键决策与放弃的备选

| 决策 | 备选与放弃原因 |
| --- | --- |
| 注入原版供应器而不是新增方块 | 新增方块要玩家换设备；注入对现有存档/布局零改动 |
| 用 `@Inject` 而非 `@Redirect` 改 `expectedOutputs` | `@Redirect` 更脆（依赖具体调用点）；`extractPatternInputs` 的 RETURN 稳定 |
| 需求④按"任务需求"过滤而不是给样板加概率字段 | 加字段要改样板编码 UI 与玩家习惯；GT 配方本来就有概率信息 |
| 每样板槽用**虚拟电路槽**而不是把电路物品留在槽里 | 电路物品会逐次累积；虚拟槽不占物品、不被消耗、槽空即清除 |
| 电路默认"免库存"（临时构造后丢弃） | 借用模式要求网络备货 N 个（AE2 计划按每次合成计数） |
| 退料取三条路径 | 只用 Forge 物品栏时，GT 输入槽"只进不出"、ME总线库存在 AE 存储上，都会静默失败 |

## 5. 实现过程（按需求）

### 需求① 不消耗物品回网
`RecipeLogic#onRecipeFinish` → `CraftTracker#onRecipeFinished` → settle → 机器空闲 20 tick 后 `cleanup`：多方块调 `InternalSlot#refund()`；单体/总线按 **三条路径**取余料 → 回网（塞不下就放供应器返还槽）。

### 需求② 编程电路
* 样板里有电路 → 读出编号，写进 `IHasCircuitSlot#getCircuitInventory()`（零件如输入总线同样实现该接口）；
* 样板里没电路 → `RecipeChanceResolver#circuitHint` 从 GT 配方推断（`IntCircuitIngredient` 的物品形态带
  `Configuration` 标签，可直接读出编号）；候选配方电路不一致时**不猜**；
* 只有**确实写入成功**才剥掉电路物品，否则保持原版，避免配方永久失配；
* 免库存：`tryExtractInitialItems` 里对电路的 `MEStorage.extract` 直接返回足量（构造物在推送时被丢弃，不会复制进网络）。

### 需求③ 概率产物补料重试
`RecipeChanceResolver#chancedOutputs` 判定概率输出 → 每次配方完成后 `neededChancedKeys`（既"没到手"又"任务需要"）→ `repush`：从网络取料、重新推送（单体插机器、多方块 `buffer.pushPattern`），上限 `chance.maxRetries`（0 = 不限）。

### 需求④ 不需要就不等
`CraftDemand#isNeeded` 从合成 CPU 内部状态精算需求（最终产物剩余量 + 未推送任务的输入需求 − CPU 暂存）， `CraftingCpuHelperMixin` 把不需要的非主产物从 `expectedOutputs`/`waitingFor` 剔除 → 主产物到手即完成、不重试。

### 需求⑤ 副产物可被 AE 读取
`NetworkCraftingProvidersMixin` 为**每个输出**建索引 → 请求副产物也能找到该样板并规划合成。

## 6. 验证过程

### 6.1 能自动验证的（都做了）

| 手段 | 结果 |
| --- | --- |
| 离线编译打包 | `BUILD SUCCESSFUL`；产物结构与清单正确 |
| **注入点对真实 jar 逐条核对** | 用 `javap -p -classpath <jar>` 核对类名/方法描述符/私有字段/包私有内部类/`@Redirect` 调用点（含 `javap -c` 确认 `MEStorage.extract` 调用确实存在）→ `docs/mixin-target-audit.txt` |
| Mixin 配置可被发现 | 故意写入一个不存在的 mixin 做探针，日志出现 `Mixin prepare failed preparing zzz… in gtae.mixins.json`，证明配置被 Mixin 读取处理 |
| 无上游源码/jar 混入产物 | 检查 jar 内容与发布包 |

### 6.2 无法在开发环境验证的（如实记录）

`runServer` 在启动早期被 **AE2 自己**的 mixin 阻断：

```
FATAL Mixin apply failed ae2.mixins.json:spatial.MinecraftServerMixin
      -> net.minecraft.server.MinecraftServer:
      InvalidMixinException @Shadow field f_129762_ was not located …
      Using refmap ae2.mixins.refmap.json
```

原因：AE2 15.4.10 生产 jar 的 refmap **缺少该 `@Shadow` 字段条目**（只有同名方法的条目），而开发环境用官方名称（`levels`）无法定位 SRG 名。 **生产环境不受影响**（SRG 名与目标类一致，无需 refmap 重映射）。

尝试过的绕过（均无效）：加 `mixin.env.remapRefMap` + `refMapRemappingFile`、用补全 refmap 的 AE2 副本替换运行依赖（批量补了 9 条字段映射）、classpath 覆盖同名 refmap。

→ 因此**功能验证必须由实机完成**，这也直接造就了下面的第 7 章。

## 7. 实机反馈驱动的三轮修复（本项目最有价值的部分）

### 7.1 第一轮：3/4/5 生效，1/2 完全不生效 → 1.0.1

**现象**：需求③④⑤正常，需求①②毫无反应。

**分析**：①②都挂在同一步「找相邻 GT 目标」，而它当时只认 `IRecipeLogicMachine`（单方块机器/控制器）； ③④⑤全在 AE2 侧，不经过目标识别——这个"对照实验"直接指向了目标识别。

**根因**：供应器推料目标是**多方块零件**（输入总线 / ME输入总线）时被整体跳过，于是一整条机器侧逻辑静默失效。

**修复**：把目标拆成 `itemHost`（收料/退料）与 `workMachine`（跑配方），并把电路写进该总线自己的电路槽；补充"写不进电路槽就不剥电路"的安全兜底。

### 7.2 第二轮：`找到 GT 目标=3` 但 `写入电路=0` → 1.0.2

**日志证据**（你提供的 `latest.log` + `/gtae status`）：

```
样板供应器钩子=3  找到 GT 目标=3  未找到=0
写入电路=0        退回余料=0      补料重试=0
副产物登记样板=8
```

**根因**：需求②的原文是「当**配方**涉及编程电路时，AE 自动把机器变成对应电路」，而 1.0.1 只实现了「**样板里**编了电路才写」。样板没编电路 → 不写电路（还可能把电路槽清零） → 配方永远匹配不上 → 机器不开工 → 余料自然也不会产生（①②一起失效的第二个原因）。

**修复**：新增 `circuit.autoDetectFromRecipe`（默认开）——从该机器可跑的 GT 配方推断电路；同时把"机器迟迟不开工就丢弃跟踪"改成"任务结束再清理退料"；诊断细化（`机器开工 / 配方完成 / 清理次数` + 挂起记录列表，电路来源区分"样板编码/配方推断/无电路槽"）。

### 7.3 第三轮：只剩退料不生效 → 1.0.3

**分析**：①②的共同点已经消除（目标识别、电路都好了），剩下的 ① 依赖"从机器里把余料取出来"。当时只有一条取料路径——Forge 物品栏，而：
* GT 机器的输入槽对外**只进不出**（AE2 能推进去，不代表能抽出来）；
* ME输入总线的库存是 `ExportOnlyAEItemList`，挂在 **AE 存储**上，不在 Forge 物品栏里。

**修复**：三条取料路径依次尝试 —— ① 直接读 `MetaMachine#getTraits()` 里的 `NotifiableItemStackHandler.storage`（绕过能力与侧面权限）→ ② AE 存储 `Capabilities.STORAGE` → ③ Forge 物品栏；并加"任务已结束时退而取回所有已推送余料"的保底；新增 `退料扫描` 计数用于区分 "没扫描"与"扫描了但没料"。

### 7.4 诊断体系是"被逼出来的"

| 版本 | 新增诊断能力 |
| --- | --- |
| 1.0.1 | `/gtae status` 计数（钩子触发、目标找到/未找到、写入电路、跟踪数、退回余料、补料重试） |
| 1.0.2 | `机器开工 / 配方完成 / 清理次数` + **挂起记录列表** + 电路来源细分 + 找不到目标时打印 6 个相邻方块类型 |
| 1.0.3 | `退料扫描` + 取料失败的方块类型日志 |

## 8. 发布准备

## 9. 发布全流程（可照抄）

### 9.1 构建

```powershell
# 离线（本机）
$env:GRADLE_USER_HOME = 'E:\work\GTAE\.ghome'
C:\gradle-8.8\bin\gradle.bat --offline --no-daemon build

# 联网（他人）
powershell -ExecutionPolicy Bypass -File scripts\fetch-libs.ps1
./gradlew build
```

产物：`build/libs/gregnuovo-1.1.0.jar`。

### 9.2 推到 GitHub

```bash
# 解压 dist/GregNuovo-1.1.0-src.zip 后在目录内执行
git init
git add .
git commit -m "GregNuovo 1.1.0"
git branch -M main
git remote add origin https://github.com/<用户名>/GregNuovo.git
git push -u origin main
```

### 9.3 建 Release

1. GitHub → Releases → Draft a new release；
2. Tag：`v1.1.0`；标题：`GregNuovo 1.1.0`；
3. 附件上传 `gregnuovo-1.1.0.jar`（可加 `-sources.jar`）；
4. 说明直接抄 `CHANGELOG.md` 的 1.1.0 段落。

### 9.4 发 Modrinth / CurseForge

* 填 **License = LGPL-3.0**、源码链接、Issue 链接；
* 依赖填 `gtceu`、`ae2`（可选填 LDLib / Architectury / Configuration / GuideME 为前置）；
* 图标用 `src/main/resources/icon.png`（若有 256×256 更佳）；
* 版本号与支持的 MC/Forge 版本要与 `mods.toml` 一致；
* **不要**上传上游 jar；不要声称与 AE2/GTM 团队有关联。

### 9.5 换上游版本时的重核清单

1. 用 `javap -p -classpath <新jar>` 重新核对 `docs/mixin-target-audit.txt` 里的**每一条**注入点
   （类名、方法描述符、私有字段、包私有内部类、`@Redirect` 调用点）；
2. 更新 `libs/` 文件名与 `gradle.properties` / `build.gradle`；
3. 跑 `./gradlew build`，并在实机开 `misc.debugLog` 验证五项功能；
4. 更新 `CHANGELOG.md`。

## 10. 踩坑清单（可复用经验）

1. **HTTPS 出网不可用**时，Gradle 依赖只能靠本地 jar + 缓存迁移；`GRADLE_USER_HOME` 必须放在可写目录。
2. Gradle daemon 可能卡死 → 用 `--no-daemon`。
3. **上游 GitHub HEAD ≠ 你手上的版本**：一切以 tag 源码 + 同版本 jar 双核对。
4. GT 的 `chance == 0` 是 **notConsumable**，不是"0% 概率"。
5. 电路槽**不能用 Forge 能力写**，必须 `setStackInSlot`。
6. AE2 只按**主产物**登记可合成项 → "副产物可请求"必须自己注入。
7. 只认 `IRecipeLogicMachine` 会漏掉**多方块零件**（总线）→ 目标识别要区分 itemHost / workMachine。
8. GT 输入槽**对外只进不出**；ME输入总线库存在 **AE 存储**上 → 取料要多路径。
9. AE2 生产 jar 的 refmap 可能缺 `@Shadow` 条目 → 开发环境跑不起整合包，**别把它当成自己的 bug**。
10. 用 PowerShell 批量替换文件内容时注意编码（曾把 `gradle.properties` 写成非法 UTF-8）。
11. 改包名时**必须同步** Mixin 配置的 `package` 字段，否则注入全部失效。
12. 诊断先行：这个模组的每个真问题都是靠 `/gregnuovo status` + `debugLog` 日志定位的，
    新功能请顺手挂上计数。
