# GregNuovo —— 五项需求实现说明

> 目标版本：MC 1.20.1 / Forge 47.4.10 / GTM 1.20.1-7.3.0 / AE2 15.4.10
> 所有注入点均已对**真实 jar** 逐条核对，结果见 `docs/mixin-target-audit.txt`。

---

## 0. 总览

### 0.1 目标识别（关键）

AE2 样板供应器推料的相邻目标**不一定是单方块机器**，常见有三种：

| 相邻方块 | itemHost（收料/退料） | workMachine（跑配方） | 电路写到 |
| --- | --- | --- | --- |
| GT 单方块机器（研磨机等） | 机器本体 | 机器本体 | 机器电路槽 |
| GT 输入总线 / ME输入总线（多方块零件） | 该总线 | 总线所属的多方块控制器 | 总线的电路槽 |
| GTM ME样板总成（多方块零件） | 样板总成缓冲 | 所属控制器 | 该样板槽自己的虚拟电路槽 |

需求1/2 都挂在“目标识别”上；识别不到就会完全静默（3/4/5 走 AE2 侧，不受影响）。 `MachineAccess#resolveTarget` 扫描 6 个相邻方块，并用“已经推进去的物品”在多个候选里挑出真正收料的那一个。

```
             ┌──────────────────────── AE2 合成CPU（CraftingCpuLogic）────────────────────────┐
玩家请求 ──► │ 规划 → 遍历任务 → pushPattern(样板, 输入)                                        │
             └───────────────┬───────────────────────────────────┬──────────────────────────┘
                             │                                   │
              [单方块/总线] 原版 AE2 样板供应器          [多方块] GTM ME样板总成
              PatternProviderLogicMixin                 MEPatternBufferMixin
                             │                                   │
                             ▼                                   ▼
                  resolveTarget() 找相邻目标                 多方块控制器
                             └──────────────┬────────────────────┘
                                            ▼
                            RecipeLogic#onRecipeFinish（精确完成时刻）
                                            ▼
                                     CraftTracker（每 tick）
                     ┌──────────────────────┼──────────────────────┐
                     ▼                      ▼                      ▼
              需求4：不需要 → 不重试   需求3：需要但没出 → 补料   需求1：退余料 + 清电路
```

### 0.2 自诊断

`/gregnuovo status`（需 OP）打印各项计数，用来判断功能是否真的跑起来了：

```
样板供应器钩子=… 样板总成钩子=…        ← 为 0 表示对应注入点没生效
找到 GT 目标=… 未找到=…                ← 未找到 > 0 时会同时打印相邻方块类型
写入电路=… 清除电路=…                  ← 需求2
退回余料=… 补料重试=…                  ← 需求1 / 需求3
副产物登记样板=… 剔除多余等待=…         ← 需求5 / 需求4
```

首次命中样板供应器 / 样板总成钩子时各打一条 INFO 日志，用于确认模组确实在工作。

涉及文件：`core/CraftTracker.java`、`hook/GNHooks.java`、`core/CraftDemand.java`、 `core/RecipeChanceResolver.java`、`core/MachineAccess.java`、`core/SlotCircuitHandler.java`。

## 1. 需求1：不消耗物品退回 AE

**目标**：配方里的“不消耗物品”（模具、催化剂等）在配方结束后回到 AE 网络，而不是永远躺在机器里。

**实现**

| 步骤 | 代码 |
| --- | --- |
| 识别“哪些输入是不消耗的” | `RecipeChanceResolver#notConsumableInputs`：用样板输出+输入匹配 GT 配方，取 `Content.chance == 0` 的输入（GTM 7.3.0 用 `chance == 0` 标记 `notConsumable`） |
| 记录本次推了什么 | `GNHooks#beforeProviderPush` → `GNState#snapshotHolder`（推送前快照，推送成功后存入 `PendingCraft.pushed`） |
| 判断配方结束 | `RecipeLogicMixin` → `RecipeLogic#onRecipeFinish` → `CraftTracker#onRecipeFinished`（多方块时由控制器触发） |
| 退料 | `CraftTracker#cleanup` → 单方块/总线：`MachineAccess#extractLeftovers`（取回 `pushed` 预算内、且属于“不消耗键”的余料）→ `StorageHelper.poweredInsert` 回网；多方块样板总成：`InternalSlot#refund()`（GTM 自带的退回逻辑） |

**取料走三条路径（v1.0.3 起）**，因为不同方块把库存暴露在不同地方：

| 顺序 | 路径 | 覆盖对象 |
| --- | --- | --- |
| 1 | 直接读 GT 内部处理槽 `MetaMachine#getTraits()` 里的 `NotifiableItemStackHandler.storage` | GT 单方块机器 / 输入总线（**不受 Forge 能力与侧面权限限制**：GT 的输入槽对外往往只进不出） |
| 2 | AE 存储 `Capabilities.STORAGE` | ME输入总线 / 样板总成这类把库存挂在 AE 网络上的方块 |
| 3 | Forge 物品栏 `getItemHandlerCap` | 普通容器与其它 mod 的机器 |

过滤规则：排除样板产物；若从 GT 配方识别出了“不消耗输入”，则优先只取这些键； **任务已结束**且过滤后一无所获时，退而取回所有“本次推送且仍在机器里”的余料（`pushed` 预算内，不会多拿）。

> 注意：**ME输入总线**的库存是 AE 网络的视图（`ExportOnlyAEItemList`），推进去的物品会直接回到网络，
> 机器的 notConsumable 输入本来就没离开网络 —— 这种情况下“没有余料可退”是正常且正确的行为。
> `/gregnuovo status` 里 `退料扫描` 有计数但 `退回余料` 为 0，通常就是这种结构。
| 时机 | 进入 `CLEANUP` 阶段后，等机器**连续空闲 20 tick** 再退料，避免抢走下一炉的原料 |

**退回目标的优先级**：直接进 ME 网络存储 → 塞不下时放进样板供应器的返还库存（下 tick 自动注入网络）。

**边界**：AE2 的合成计划会按“每次合成”计入输入数量，所以一次作业要用 N 次模具时，网络里仍需备够 N 个（用完会如数退回）。这一条是 AE2 计划器的行为，本模组只保证“用掉多少、退回多少”。

## 2. 需求2：编程电路自动写入机器

**目标**：样板里编入的 GT 编程电路（`gtceu:programmed_circuit`）不作为物品推送，而是写进机器电路槽；不消耗网络库存；样板没有电路时把机器电路清零。

### 2.1 单方块机器 / 输入总线

| 步骤 | 代码 |
| --- | --- |
| 识别电路 | `GNHooks#circuitOrNull`：遍历样板输入，`IntCircuitBehaviour.getCircuitConfiguration` 取编号（0..32） |
| 找目标 | `MachineAccess#resolveTarget`：相邻的 GT 机器**或**多方块零件（输入总线 / ME输入总线） |
| 写入机器 | `MachineAccess#setCircuitOn` → `IHasCircuitSlot.getCircuitInventory().setStackInSlot(0, IntCircuitBehaviour.stack(n))`（GT 自己 `IntCircuitBehaviour#useOn` 的同款路径；电路槽**不能**用 Forge `ITEM_HANDLER` 写入） |
| 不作为物品推送 | 仅在**确实写入了电路槽之后**才 `PatternAnalyzer#stripCircuits`；目标没有可写电路槽时保持原版行为（电路继续作为物品推送），避免配方永远匹配不上 |
| 不消耗库存（默认） | `CraftingCpuHelperMixin` 重定向 `tryExtractInitialItems` 里的 `MEStorage.extract`：对电路直接“返回足量”，即临时构造；推送时被丢弃，所以既不需要库存、也不会复制进网络 |
| 不消耗库存（`stockless=false`） | 从网络借出后，推料前立刻 `StorageHelper.poweredInsert` 原样退回 |
| 清零 | 样板无电路且 `clearWhenAbsent=true` → 电路槽清空；合成结束且 `clearAfterCraft=true` → 清掉本模组写入的电路 |

### 2.2 多方块（ME样板总成，每个样板槽独立电路）

GTM 7.3.0 的 `InternalSlotRecipeHandler$SlotRHL` 构造器把**同一个**共享电路槽加进了全部 27 个样板槽，因此多个不同电路的样板会互相干扰。本模组的做法：

| 步骤 | 代码 |
| --- | --- |
| 摘掉共享电路槽 | `SlotRHLMixin`（`@Inject <init> TAIL`）从该槽位 handler 列表里移除 `buffer.getCircuitInventory()` |
| 插入虚拟电路槽 | 同上，`addHandler(new SlotCircuitHandler(...))`：把该样板槽自己的电路编号当作“插在机器上的编程电路”参与配方匹配，匹配即满足且**不消耗** |
| 电路来源 | `GNHooks#beforeBufferPush` → `GNState#setSlotCircuit(buffer, index, n)`（按样板槽下标存储） |
| “完成后清除” | `SlotCircuitHandler` 只在该样板槽**有内容时**才提供电路；槽空了（配方做完）即视为清除；样板被换掉时 `MEPatternBufferMixin#onPatternChange` 也会清掉 |
| 同样剥掉物品推送 | `PatternAnalyzer#stripCircuits`，库存处理同单体机器 |

> 注意：接管电路匹配后，样板总成 GUI 里那个“共用电路槽”不再参与配方匹配（本模组用它来表达“每个样板各自的电路”）。

## 3. 需求3：概率产物没出就继续补料

**目标**：当前合成任务**需要**某个概率产物、但这次投料没产出时，继续投料直到产出。

**哪些输出算概率产物**：`RecipeChanceResolver#chancedOutputs`。 AE2 的样板 NBT 里没有概率字段，所以概率信息全部来自 GT 配方：用“样板输出 + 样板输入”匹配机器可运行的配方类型（`GTRecipeType#getCategoryMap`），取输出 `Content#isChanced()`（`0 < chance < maxChance`）的输出键。

**重试流程**（`CraftTracker`）：

1. `RecipeLogic#onRecipeFinish` 触发（`RecipeLogicMixin`），宽限 5 tick 让产物落地；
2. `neededChancedKeys`：对每个概率输出键，要求 **`cpu.getWaitingFor(key) > 0`（还没到手）** 且
   **`CraftDemand.isNeeded(cpu, key)`（任务确实需要）**；
3. 需要 → `repush`：
   * 用 `PatternAnalyzer#expandInputs` 把样板输入展开成 `KeyCounter[]`（剥掉电路）；
   * 从 ME 网络按量抽取（`StorageHelper.poweredExtraction`），抽不齐就整体回滚，不半途投料；
   * 单体机器：写电路 + 插入机器物品栏；多方块：`buffer.pushPattern(...)`（`GNState#setRepushing` 防止重复登记）；
   * 重试次数 +1，回到“等待机器开工”状态；
4. 上限 `chance.maxRetries`（0 = 不限），间隔 `chance.retryIntervalTicks`。

> 多炉连续运行时机器可能一直不空闲，因此完成判定用的是 `onRecipeFinish` 事件而不是轮询状态。

## 4. 需求4：任务不需要的概率产物，立刻停止

**目标**：样板里编了 50% 的副产物 B，但这次合成只要主产物 A —— A 到手就结束，不为 B 空等、也不重试。

**判定“需不需要”**：`CraftDemand#isNeeded(cpu, key)`，从合成 CPU 的内部状态精确推算：

```
需要量 = (最终产物是该键 ? 剩余未交付数量 : 0)
       + Σ 尚未推送完成的样板任务（job.tasks）里把该键当输入的需求量 × 剩余次数
是否需要 = 需要量 > CPU 内部已暂存量
```

* 最终产物（`finalOutput` / `remainingAmount`）**永远视为需要**，避免作业永远无法完成；
* 读取这些内部状态用三个 accessor mixin：`CraftingCpuLogicAccessor`、`ExecutingCraftingJobAccessor`、`TaskProgressAccessor`；
* 任何异常都保守返回“需要”，不会误判成不需要。

**让 AE 也不等**：`CraftingCpuHelperMixin` 在 `extractPatternInputs` 返回时，把“非主产物且任务不需要”的键从 `expectedOutputs` 中剔除，于是它们不会进入 `job.waitingFor`：

* 主产物到手即完成（AE2 的完成判定本来就只看最终产物）；
* 顺带把 `getWaitingFor(key)` 变成干净的“确实需要但还没到手”信号，供需求3 使用；
* 不需要的副产物产出后直接落到普通 ME 存储，不被 CPU 截留。

**结果**：不需要 → 不等待、不重试、材料一停到底（`neededChancedKeys` 返回空 → 进入退料清理）。

## 5. 需求5：AE 能读到样板里写出的副产物

**问题**：AE2 原版只用样板的**主产物**（`getOutputs()[0]`）登记“可合成项”（`NetworkCraftingProviders$ProviderState#mount`），所以样板里另外写出的副产物 B 在终端里既不是“可合成”，请求 B 时也找不到这个样板。

**实现**：`NetworkCraftingProvidersMixin`

| 注入 | 作用 |
| --- | --- |
| `addProvider` TAIL | 遍历该供应器的全部样板，把**每一个输出**都建索引（副产物也登记） |
| `removeProvider` TAIL | 同步移除 |
| `getCraftingFor` RETURN | 原版结果为空时，回退到本索引（样板规划取样板就靠这个入口，`CraftingTreeNode:87/127`） |
| `getCraftableKeys` / `getCraftables` | 让终端把副产物也显示为可合成 |

**效果**：请求 B → 规划器找到“A + 50%B”的样板 → 需要量按 B 计算 → B 成为任务需要的产物 → 需求3 的重试开始工作，直到 B 产出；不出 B 就一直补料，出够即停。

> 该功能受 `chance.byproductCraftable` 控制，默认开启。若只想恢复原版行为可关闭。

## 7. 上机验证方法（建议按顺序做）

1. **需求2（单体）**：放一台 GT 机器（如研磨机）+ 原版样板供应器；样板输入放 `编程电路 = 5` + 原料，输出写产物。
   终端请求合成 → 机器电路槽应自动变成 5，电路不进机器物品栏，网络里 0 个电路也能开工。换成没有电路的样板 → 电路槽应被清零。
2. **需求2（多方块）**：给多方块装上 ME样板总成，放两个电路不同的样板（如 1 和 5），
   分别请求 → 两个样板互不干扰；配方做完后电路视为清除。
3. **需求1**：配方里带模具（如挤压机 + 模具）→ 合成结束后模具应回到 ME 网络（终端可见），机器里不留。
4. **需求3**：样板写“主产物 A（100%）+ 副产物 B（50%）”；先请求 B → 应反复投料直到 B 产出。
5. **需求4**：同一块样板，只请求 A → A 到手任务即结束，不因 B 缺失而卡住、也不额外投料。
6. **需求5**：副产物 B 未在样板主输出位时，终端请求 B 也应能找到该样板并自动合成（`byproductCraftable=true`）。
7. 打开 `chance.debugLog` 可以看到每次登记 / 补料 / 退料的日志。

## 8. 与上游行为的差异（需要注意）

1. 样板总成原版的“共用电路槽”不再参与配方匹配（由每个样板槽自己的电路取代）。
2. `byproductCraftable=true` 时，样板里写出的**所有**输出都会变成“可自动合成”，
   包括非 GT 的样板；如不喜欢可关闭该开关。
3. 概率判定依赖“样板 ↔ GT 配方”匹配。匹配不到唯一配方时按确定性处理（不重试）。
4. 重试是真实投料（会消耗材料），这是需求3 的语义；上限可配置。

### 9.2 需求1/2 首轮失效的根因与修复（v1.0.1）

**现象**：3/4/5 生效，1/2 完全不生效。

**根因**：需求1/2 都挂在同一步「找相邻 GT 目标」上，而它原本只认 `IRecipeLogicMachine`（单方块机器/控制器）。当图案供应器推料的对象是 **多方块零件**（输入总线 / ME输入总线 / 样板总成）时：
* 零件不是 `IRecipeLogicMachine` → 目标识别返回 null；
* 于是一整条机器侧逻辑被静默跳过：不写电路（需求2）、不登记跟踪（需求1）；
* 3/4/5 全在 AE2 侧（合成 CPU / 合成索引），不经过目标识别，所以照常生效。

**修复（v1.0.1）**：
1. `MachineAccess#resolveTarget` 现在同时接受机器与多方块零件，并把目标拆成
   `itemHost`（真正收料的方块，退料/补料用它）与 `workMachine`（真正跑配方的控制器，状态判断用它）；
2. 零件（`ItemBusPartMachine` / `MEInputBusPartMachine`）本身实现 `IHasCircuitSlot` → 电路写进该总线的电路槽；
3. 只有在**确实写入电路槽之后**才剥掉电路物品，否则保持原版（防止“剥了电路又没写进去”导致配方永不匹配）；
4. 样板总成的虚拟电路槽增加了兼容回退：该样板没有自己的电路时，沿用玩家在共用电路槽上的设置；
5. 样板槽下标改为 accessor + 反射双路径（取不到不再静默失效）；
6. 新增 `/gregnuovo status` 自诊断与关键节点的首/末次日志。

**若仍不生效**，按第 10 节排查。

### 9.2.1 第二轮实机反馈 → v1.0.2

用户实测日志（GregTech Universe / Forge 47.4.10）显示：模组已加载、无任何 mixin 报错，且

```
样板供应器钩子=3  找到 GT 目标=3  未找到=0      ← 目标识别已修好
写入电路=0                                    ← 需求2 仍未触发
退回余料=0  补料重试=0
副产物登记样板=8                               ← 需求5 正常
```

**根因**：需求2 的原文是「当**配方**涉及编程电路时，AE 会自动将对应机器变成对应的编程电路」，而 v1.0.1 只实现了「**样板里**编了电路才写」。用户样板里没有编电路 → 不写电路 → 可能还把电路槽清零 → 配方永远匹配不上 → 机器不开工 → 余料自然也不会产生（两条一起失效）。

**修复（v1.0.2）**：

1. 新增 `circuit.autoDetectFromRecipe`（默认开）：样板没编电路时，从该机器可运行的 GT 配方推断电路
   （GT 用 `IntCircuitIngredient` 表达电路配方，其物品形态带 `Configuration` 标签，可直接读出编号）；多个候选配方电路不一致时**不猜**，保持机器现状并在调试日志说明；
2. 机器迟迟不开工时不再直接丢弃记录：任务仍在进行就继续等待，任务结束后自动转入清理并退回余料
   （需求1 在“配方从未匹配上”的极端情况下也能把料退回来）；
3. 诊断加细：`/gregnuovo status` 新增 `机器开工 / 配方完成 / 清理次数` 计数与**挂起记录列表**
   （每条记录处于哪个阶段、电路是多少、推了什么、重试几次），并区分 `电路来源=样板编码 / 配方推断`、 `无电路槽` 计数；目标没有可写电路槽时会打一条 WARN。

### 9.3 未完成：开发环境整体启动（与本模组无关）

`runServer` 在启动早期被 **AE2 自身**的 mixin 阻断：

```
[mixin/] FATAL Mixin apply failed ae2.mixins.json:spatial.MinecraftServerMixin
        -> net.minecraft.server.MinecraftServer:
        InvalidMixinException @Shadow field f_129762_ was not located in the target class
        net.minecraft.server.MinecraftServer. Using refmap ae2.mixins.refmap.json
```

原因：AE2 15.4.10 生产 jar 的 `ae2.mixins.refmap.json` 里**没有**该 `@Shadow` 字段的条目（只有同名方法 `createLevels` 的条目），而开发环境用的是 Mojang 官方名称（`levels`），因此 Mixin 无法把 SRG 名 `f_129762_` 解析到目标字段。 **生产环境不受影响**：正式游玩时 AE2 是生产 jar，SRG 名称与目标类一致，无需 refmap 重映射。

已尝试且**无效**的绕过方式：
1. 开发运行加 `mixin.env.remapRefMap` + `refMapRemappingFile` —— AE2 的 refmap 本身缺条目，无济于事；
2. 用补全 refmap 的 AE2 副本替换运行期依赖（含把该字段条目批量补齐 9 条）—— 仍然无法定位，放弃；
3. classpath 覆盖同名 refmap 资源 —— Mixin 从 mod 文件内部读取该资源，覆盖无效。

结论：**游戏内五项功能需要把 `build/libs/gregnuovo-1.0.0.jar` 放进真实整合包验收**，步骤见本文第 7 节；这也是本模组的目标使用方式（生产环境）。

## 10. 排查：需求1/2 仍不生效时

第 1 步：装好 jar 后进游戏，用 OP 执行 `/gregnuovo status`，按下面对照：

| 计数 | 含义 | 为 0 / 异常时的结论 |
| --- | --- | --- |
| `样板供应器钩子` | 单方块/总线路径是否被触发 | 0 → 混入没生效（检查日志有没有 mixin 报错） |
| `样板总成钩子` | 多方块样板总成路径是否被触发 | 没用到样板总成时为 0 属正常 |
| `找到 GT 目标` | 相邻目标识别成功次数 | 0 且 `未找到` > 0 → **看紧随其后的 WARN 日志**，里面会列出 6 个相邻方块的实际类型 |
| `写入电路`（样板编码 / 配方推断 / 无电路槽） | 需求2 | 全 0 → 该配方不需要电路；`无电路槽` > 0 → 目标方块没有 `IHasCircuitSlot`（电路按原版当物品推送，日志有 WARN） |
| `机器开工` | 跟踪的合成里机器是否真的跑起来 | 0 → 配方没匹配上（电路/等级/输入），此时看第 2 步日志 |
| `配方完成` | 是否收到 `onRecipeFinish` 并命中记录 | 0 且 `机器开工` > 0 → 完成回调没挂上（记录一下告诉我们） |
| `清理次数` | 退料流程执行次数 | > 0 但 `退回余料` = 0 → 确实没有不消耗余料 |
| `退回余料` | 需求1 | 一直 0 → 没有余料，或机器从未开过工（v1.0.2 起任务结束也会兜底退回） |
| `补料重试` | 需求3 | 一直 0 → 概率产物已到手，或该键被判定为“任务不需要” |
| `副产物登记样板` / `剔除多余等待` | 需求5 / 需求4 | 为 0 说明样板输出或缓存判断有问题 |
| `挂起记录` | 每条卡住的合成处于哪个阶段 | 长期停在 `WAITING_WORK` = 机器一直没开工；停在 `CLEANUP` = 机器一直没空闲 |
